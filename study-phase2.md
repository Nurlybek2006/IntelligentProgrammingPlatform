# Phase 2: аутентификация, пайдаланушылар және есептерді басқару

Бұл кезең Phase 1-дегі дерекқор мен модельдердің үстіне жасалды. Қолданыстағы `ApplicationDbContext`, модельдер, байланыстар және `InitialCreate` миграциясы сақталды. Жоба қайта құрылмады.

## 1. Phase 2-де не жасадық?

Пайдаланушыны тіркеу, жүйеге кіргізу, шығару және профиль бетін қостық. Екі рөл бар: `Student` және `Admin`. Әкімші тақырыптарды, бағдарламалау есептерін және тест деректерін басқара алады. Қонақтар мен студенттер жарияланған есептерді және олардың ашық мысалдарын қарай алады.

Барлық әрекет MVC контроллерлері арқылы орындалады. Контроллерлер дерекқорға EF Core арқылы, ал аккаунттарға Identity қызметтері арқылы қатынайды. Қосымша repository, MediatR, AutoMapper немесе басқа күрделі қабаттар енгізілген жоқ.

```text
Browser
   |
   v
Controller
   |
   +---- Identity
   |       |
   |       +---- AspNetUsers
   |       +---- AspNetRoles
   |       +---- AspNetUserRoles
   |
   +---- ApplicationDbContext
           |
           +---- Topics
           +---- ProgrammingTasks
           +---- TestCases
```

## 2. ASP.NET Core Identity деген не?

Identity — аккаунттарды, парольдерді, рөлдерді және кіруді басқаруға арналған ASP.NET Core кітапханасы. Ол пароль тексеру, хэш сақтау, қате кіру әрекеттерін санау және аутентификация cookie-сін жасау сияқты жұмыстарды орындайды.

`Program.cs` ішінде `AddIdentity<ApplicationUser, IdentityRole>()`, `AddEntityFrameworkStores<ApplicationDbContext>()` және `AddDefaultTokenProviders()` тіркелді. MVC беттерін өзіміз жасадық; JWT қолданылмайды. Тіркеу мен cookie конфигурациясының негізі [ASP.NET Core Identity ресми құжаттамасында](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity?view=aspnetcore-10.0) түсіндірілген.

Пароль кемінде 8 таңбадан тұрып, үлкен әріп, кіші әріп, сан және арнайы таңба қамтуы керек. Тіркелу формасында ең ұзын пароль 100 таңба деп шектелген. Email бірегей болуы тиіс. Бес қате кіру әрекетінен кейін аккаунт уақытша бес минутқа бұғатталады. Email растау жүйесі бұл кезеңде қосылған жоқ.

## 3. ApplicationUser не үшін керек?

`ApplicationUser` — Phase 1-де жасалған пайдаланушы моделі. Ол `IdentityUser` класынан мұра алады және `DisplayName`, `CreatedAt` өрістерін қосады. Пайдаланушының стандартты `string Id` идентификаторы өзгерген жоқ.

Аккаунт деректері `AspNetUsers` кестесіне жазылады. `DisplayName` навигация мен профильде көрсетіледі. `CreatedAt` серверде UTC уақытымен беріледі. Браузер жіберген уақытты немесе рөлді аккаунтқа тікелей көшірмейміз.

## 4. UserManager деген не?

`UserManager<ApplicationUser>` аккаунтты қауіпсіз басқаруға көмектеседі. Мысалы, `CreateAsync(user, password)` пароль талабын тексеріп, пайдаланушыны сақтайды. `FindByEmailAsync` email бойынша іздейді, `AddToRoleAsync` рөл қосады, `GetRolesAsync` пайдаланушы рөлдерін оқиды.

Контроллер пароль хэшін өзі есептемейді. Identity-дің дайын әдістерін пайдалану арқылы оның тексерулері мен сақтау тәртібін сақтаймыз.

## 5. SignInManager деген не?

`SignInManager<ApplicationUser>` кіру және шығу әрекеттерін басқарады. `PasswordSignInAsync` парольді тексереді және сәтті болса аутентификация cookie-сін жасайды. Жаңа тіркелген студентті `SignInAsync` арқылы бірден кіргіземіз. `SignOutAsync` арқылы шығарамыз.

`RememberMe` белгіленсе, cookie браузер жабылғаннан кейін де сақталуы мүмкін. Біз cookie мерзімін жеті күнге қойдық және белсенді қолдану кезінде мерзімін жаңартуды қостық.

## 6. RoleManager деген не?

`RoleManager<IdentityRole>` рөлдердің өзін басқарады. `Data/DbSeeder.cs` іске қосылғанда `RoleExistsAsync` арқылы `Student` және `Admin` бар-жоғын тексереді. Жоқ рөл ғана жасалады.

Рөл анықтамасы `AspNetRoles` кестесінде, пайдаланушының рөлге мүшелігі `AspNetUserRoles` кестесінде сақталады. Рөл атаулары қайталанып қате жазылмауы үшін `Models/RoleNames.cs` тұрақтылары қолданылды.

## 7. Cookie authentication қалай жұмыс істейді?

Кіру сәтті аяқталғанда сервер қорғалған аутентификация cookie-сін браузерге береді. Кейін браузер осы сайтқа сұрау жібергенде cookie-ді қоса жібереді. Сервер оны тексеріп, `HttpContext.User` объектісін толтырады.

Cookie парольді сақтамайды. `HttpOnly` JavaScript-тің оны оқуына кедергі жасайды; `SameSite=Lax` басқа сайттан келетін кейбір сұрауларда жіберілуін шектейді. HTTPS арқылы кіргенде cookie `Secure` белгісімен беріледі.

Middleware реті маңызды:

```csharp
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
```

Алдымен пайдаланушы кім екенін анықтаймыз, одан кейін оның осы әрекетке рұқсаты бар-жоғын тексереміз.

## 8. Student және Admin рөлдерінің айырмашылығы

```text
Anonymous
   |
   +---- Жарияланған есептерді және ашық мысалдарды қарау
   +---- Register / Login

Student
   |
   +---- Жарияланған есептерді қарау
   +---- Өз профилін қарау
   +---- Logout

Admin
   |
   +---- Профиль және есептер каталогы
   +---- Topics CRUD
   +---- Programming Tasks CRUD
   +---- Test Cases CRUD
```

Кәдімгі тіркелу әрқашан `Student` рөлін береді. Тіркелу формасында рөл таңдау жоқ. Сұрауға қолдан `Role=Admin` қосылса да, ол тіркелу ViewModel-інде жоқ және әкімші құқығын бермейді.

Даму әкімшісі тек жергілікті конфигурациядан жасалады. Оның рөлі — `Admin`; ол жалпыға ашық каталогты да қарай алады.

## 9. [Authorize] не істейді?

`[Authorize]` жүйеге кірген пайдаланушыны талап етеді. Мысалы, профиль анонимді пайдаланушыға ашылмайды.

`[Authorize(Roles = RoleNames.Admin)]` тек әкімші рөлін талап етеді. Admin аймағындағы барлық төрт контроллерде осы атрибут бар. Студент батырманы көрмесе де, URL немесе POST сұрауын қолдан жіберуі мүмкін. Сондықтан рұқсатты сервер тексереді.

Анонимді сұрау Login бетіне бағытталады. Жүйеге кірген, бірақ рөлі жетпейтін пайдаланушы AccessDenied бетіне бағытталады; бұл бет HTTP 403 қайтарады. Аккаунт және Admin беттерінде `Cache-Control: no-store` қолданылады.

## 10. Register қалай жұмыс істейді?

1. Браузер `RegisterViewModel` өрістерін және anti-forgery token жібереді.
2. Сервер міндетті өрістерді, email пішімін, мәтін ұзындығын және парольдердің сәйкестігін тексереді.
3. Email бұрын тіркелгенін тексереді.
4. `ApplicationUser` жасалып, `UserName = Email`, `Email`, `DisplayName`, серверлік `CreatedAt` беріледі.
5. `UserManager.CreateAsync` аккаунт пен пароль хэшін сақтайды.
6. `Student` рөлі қосылады.
7. Транзакция бекітілгеннен кейін пайдаланушы жүйеге кіріп, профильге өтеді.

Аккаунт жасау мен Student рөлін қосу бір транзакцияда орындалады. Бір қадам сәтсіз болса, транзакция бекітілмейді; толық тіркелмеген аккаунтқа cookie берілмейді.

## 11. Login қалай жұмыс істейді?

Сервер email бойынша аккаунтты тауып, `PasswordSignInAsync` шақырады. Қате парольге де, табылмаған email-ге де бірдей `Invalid email or password.` хабарын көрсетеді. Бұл жауап аккаунттың бар-жоғын ашып бермейді.

`lockoutOnFailure: true` қате кіру әрекеттерін есептеуге мүмкіндік береді. `returnUrl` тек `Url.IsLocalUrl` арқылы тексерілген жергілікті URL болса қолданылады. Сыртқы сайтқа бағыттайтын мән қабылданбайды.

## 12. Logout неге POST арқылы жасалады?

Шығу пайдаланушы сессиясын өзгертеді, сондықтан оны GET сілтемесімен жасамаймыз. Навигацияда `method="post"` формасы бар; оның батырмасы `Account/Logout` әрекетін шақырады.

Сервер anti-forgery token-ді тексеріп, `SignOutAsync` орындайды. GET арқылы Logout шақыру қолдау таппайды.

## 13. Пароль дерекқорда қалай сақталады?

Identity ашық парольді сақтамайды: ол парольдің тұз қосылған хэшін `AspNetUsers.PasswordHash` бағанына жазады. Кірген кезде берілген пароль осы хэшпен арнайы тексеру алгоритмі арқылы салыстырылады.

Өзіміздің `Password` бағанымыз немесе хэштеу алгоритміміз жоқ. Пароль ViewModel-де сұрауды өңдеу үшін ғана болады. Оны профильге, HTML-ге, журналға немесе оқу құжатына шығармаймыз.

## 14. User Secrets не үшін қолданылды?

Жергілікті әкімші конфигурациясы репозиторийден бөлек .NET User Secrets қоймасында сақталады:

- `SeedAdmin:Email`
- `SeedAdmin:Password`
- `SeedAdmin:DisplayName`

Жобаға `UserSecretsId` қосылды. `scripts/Set-DevelopmentAdmin.ps1` күшті кездейсоқ пароль жасайды және конфигурацияны CLI-ға standard input арқылы береді. Пароль команда аргументінде немесе экранда көрсетілмейді. Бар мәндер қайта іске қосқанда сақталады.

Даму аккаунтының email-і — `admin@local.dev`. Пароль бұл құжатта жоқ. Оны өз компьютеріңізде Visual Studio-дағы жоба мәзірінен **Manage User Secrets** арқылы жеке қарауға болады. User Secrets жергілікті даму үшін арналған; бұл өндірістік құпиялар қоймасы емес.

Seeder әкімшіні тек `Development` ортасында жасайды. Email немесе пароль жоқ болса, рөлдер жасалып, әкімші жасау өткізіледі және құпия мәндерді көрсетпейтін хабар жазылады. Бар әкімшінің паролі қайта орнатылмайды. Егер бапталған email кәдімгі пайдаланушыға тиесілі болса, оны автоматты түрде Admin-ге айналдырмаймыз.

## 15. Admin Area деген не?

Area үлкен MVC қолданбасындағы бір бөлімнің контроллерлері мен Views файлдарын бөлек ұйымдастыруға көмектеседі. Біздің құрылым:

```text
Areas/Admin/
    Controllers/
        HomeController.cs
        TopicsController.cs
        ProgrammingTasksController.cs
        TestCasesController.cs
    Views/
        Home/
        Topics/
        ProgrammingTasks/
        TestCases/
```

`[Area("Admin")]` контроллерді осы аймаққа жатқызады. Маршрут `{area:exists}/{controller=Home}/{action=Index}/{id?}` арқылы `/Admin` басқару беті ашылады. Жеке жаңа дизайн жасалған жоқ: Admin беттері де ортақ Bootstrap layout қолданады.

## 16. Topic CRUD қалай жұмыс істейді?

CRUD — Create, Read, Update, Delete: қосу, оқу, өзгерту, өшіру. Тақырып үшін `Name` міндетті және 100 таңбадан аспайды; `Description` міндетті емес, 2000 таңбаға дейін.

Create және Edit POST әрекеттері `TopicFormViewModel` қабылдайды. Атауы қалыпқа келтіріліп, SQL Server арқылы қайталану тексеріледі. Тақырып есептерде қолданылса, өшіру тоқтатылып, түсінікті хабар беріледі. Қалыпты жағдайда пайдаланушы raw SQL қатесін көрмейді.

Бір мезгілде екі сұрау өзгеріс жасаса, бастапқы тексеруден кейін де шектеу қатесі болуы мүмкін. `DbUpdateErrors` осындай жарыс жағдайларындағы unique/FK қателерін танып, қауіпсіз хабар көрсетуге көмектеседі.

## 17. ProgrammingTask CRUD қалай жұмыс істейді?

Әкімші есепті қосады, өзгертеді, толық қарайды және қауіпсіз жағдайда өшіреді. Форма тақырып пен күрделілікті dropdown арқылы таңдатады. `CreatedAt` формада жоқ; оны сервер береді және Edit кезінде өзгертпейді.

Тексерулер: Title — 200 таңбаға дейін, Slug — 200 таңбаға дейін және URL-ге жарамды пішім, Description — міндетті. Уақыт шегі 100–30000 ms, жад шегі 16–1024 MB. `TopicId` нақты тақырыпқа сілтеуі керек, ал Difficulty enum-да бар мән болуы тиіс.

`IsPublished` жариялауды басқарады. Жіберілімдері бар есеп өшірілмейді; оны каталогтан алу үшін жариялау белгісін өшіруге болады. Тек тесттері бар есепті өшіру алдында әкімші сол қолданылмайтын тесттерді жеке өшіреді. Phase 1 каскад ережелері өзгертілген жоқ.

## 18. TestCase CRUD қалай жұмыс істейді?

Негізгі жол: **Admin → Programming tasks → Task details → Test cases**. Әкімші тестің кірісін, күтілетін нәтижесін, жасырын белгісін және ретін басқарады.

`ProgrammingTaskId + Order` жұбы бірегей. Сондықтан бір есепте бірдей реттік нөмірлі екі тест сақталмайды. Басқа есепте дәл сол нөмір болуы мүмкін. `Order` 0–100000 аралығында болуы керек.

Бос Input және ExpectedOutput жарамды дерек саналады. Олардың бос орындары мен жол үзілістерін Trim арқылы жоймаймыз. Edit кезінде тесті басқа есепке көшіруге тыйым салынған. `ExecutionResults` жазбалары бар тест өшірілмейді.

## 19. IsHidden не үшін керек?

`IsHidden = false` тесттері есептің ашық мысалдары ретінде көрсетіледі. `IsHidden = true` тесттері студентке берілмеуі тиіс; болашақ тексеру жүйесі оларды сервер жағында пайдаланады.

Өрістің өзі қолжетімділікті қорғамайды. Қауіпсіздік деректерді қандай сұраумен алғанымызға және кімге қайтарғанымызға байланысты.

## 20. Hidden тесттерді студенттен қалай жасырдық?

`TasksController.Details` сұрауы екі маңызды сүзгіні қолданады:

```csharp
.Where(task => task.IsPublished && task.Slug == slug)
// TaskDetailsViewModel ішіндегі мысалдар:
task.TestCases.Where(test => !test.IsHidden)
```

Сұрау деректерді бірден `TaskDetailsViewModel` және `TaskExampleViewModel` түрлеріне проекциялайды. Жасырын тесттің Input/ExpectedOutput мәндері public ViewModel-ге мүлде түспейді. Оларды HTML-де, JavaScript-те немесе жасырын элементте жасырып қою тәсілі қолданылмайды.

Толық жауап HTML-і нақты HTTP тесттерімен тексерілді: ашық мысалдар бар, ал арнайы жасалған жасырын деректер жоқ. Әкімші беттерінде толық тесттер көрсетіледі, бірақ бұл беттерге серверлік Admin рөлі қажет.

## 21. Slug деген не?

Slug — есепті URL арқылы табуға арналған оқылатын бірегей белгі. Мысалы:

```text
/Tasks/sum-of-two-numbers
```

Қолданылған пішім: әріптер мен сандар, сөздердің арасында бір дефис. Сақтау алдында кіші әріпке айналдырылады. Бос орын, басындағы немесе соңындағы дефис қабылданбайды. Slug қайталанбауы керек. Әкімші оны формада өзі енгізе алады.

Жарияланбаған есептің Slug мәнін білсе де, қонақ немесе студент оның бетін аша алмайды: сервер 404 қайтарады.

## 22. ViewModel деген не және entity-ден айырмашылығы қандай?

Entity дерекқордағы объектіні сипаттайды. Мысалы, `ProgrammingTask` ішінде серверлік CreatedAt пен басқа объектілерге навигациялар бар. ViewModel нақты формаға немесе бетке керек өрістерді ғана ұстайды.

Task POST әрекеті `ProgrammingTaskFormViewModel` қабылдайды. Онда CreatedAt, Submissions сияқты артық өрістер жоқ. Қабылданған мәндер entity-ге қолмен көшіріледі. Бұл overposting, яғни сұрауға бөтен өріс қосып өзгерту қатерін азайтады.

Public тапсырма ViewModel-інде жасырын тесттерге арналған коллекция жоқ. Профиль ViewModel-інде пароль хэші немесе security stamp жоқ.

## 23. ModelState деген не?

`ModelState` форманы модельге айналдыру кезіндегі және DataAnnotations тексерулеріндегі қателерді сақтайды. Мысалы, `TimeLimitMs` орнына мәтін келсе немесе міндетті Title бос болса, модель жарамсыз болады.

Контроллер `ModelState.IsValid` тексереді. Қате болса, сақтау орындалмайды және сол форма қате хабарларымен қайтарылады. Қайталанған slug немесе жоқ TopicId сияқты дерекқорға тәуелді тексерулер `ModelState.AddModelError` арқылы қосылады.

Views ішінде `asp-validation-for`, `asp-validation-summary` және қолданыстағы `_ValidationScriptsPartial` бар. Клиенттік тексеру пайдаланушыға ыңғайлы; серверлік тексеру бәрібір міндетті.

## 24. Anti-forgery token не үшін керек?

CSRF шабуылында бөтен сайт пайдаланушының белсенді cookie-сін пайдаланып, оның атынан әрекет жасатуға тырысады. Anti-forgery механизмі форма token-ін cookie-дегі мәнмен тексеруге көмектеседі.

`Program.cs` ішінде жалпы `AutoValidateAntiforgeryTokenAttribute` фильтрі қосылды. POST сияқты өзгертетін сұрауларда token талап етіледі. Razor form tag helper token-ді автоматты қосады. Token-і жоқ Register, Logout және Admin POST сұраулары HTTP 400 қайтаратыны тексерілді.

## 25. Phase 1 мен Phase 2 қалай байланысады?

Phase 1 дерекқор құрылымын дайындады. Phase 2 сол кестелермен жұмыс істейтін MVC беттерін және Identity қызметтерін қосты. Entity модельдері мен `ApplicationDbContext` схемасы өзгерген жоқ.

`dotnet ef migrations has-pending-model-changes` модель өзгермегенін растады. Сондықтан бос Phase 2 миграциясы жасалмады. `dotnet ef database update` сәтті орындалып, база жаңартылған күйде екенін хабарлады. Қолданылған миграция әлі де `20260930082441_InitialCreate`.

Бір қосылымдағы MARS мүмкіндігі осы кодқа қажет емес. Тіркеудің бірнеше сақтау қадамы бар транзакциясын қосқанда EF Core MARS қосулы болса savepoint жасай алмайтынын ескертті. Сондықтан connection string-дегі `MultipleActiveResultSets=False` қойылды. Сервер, база және Windows authentication өзгерген жоқ.

Даму деректері тек Development ортасында жасалады: Basics, Arrays, Algorithms тақырыптары; Sum of Two Numbers, Maximum in Array, Fibonacci Number есептері; барлығы 8 тест, оның 5-еуі ашық және 3-еуі жасырын. Тақырып Name, есеп Slug арқылы тексеріледі. Бар есептер қайта жазылмайды; жойылған demo есеп Development ортасын қайта іске қосқанда қайта жасалуы мүмкін.

## 26. Phase 3-те не жасалады?

Келесі кезеңнің нақты талабына сәйкес код жазу мен шешім жіберу интерфейсі, содан кейін оқшауланған орындау жүйесі қосылуы мүмкін. Студент кодын веб-сервер процесінде орындауға болмайды. Болашақ runner CPU, жад, уақыт және желі шектеулері бар бөлек контейнерлерді пайдалануы тиіс.

Бұл кезеңде редактор, Submit логикасы, компиляция, judging, Docker runner, OpenAI, AI кеңестері, статистика және рейтинг есептеу жасалған жоқ. Verification сценарийіндегі Submission/ExecutionResult жазбалары тек өшіруден қорғауды тексеретін уақытша деректер; олар ешбір кодты орындамайды.

## Орындалған негізгі командалар

Бұл командалар жоба түбірінде орындалды. Build пен verification өзгерістерді тексеру барысында қайталанды. Пароль ешбір командада ашық берілген жоқ.

```powershell
git status --short
dotnet build
dotnet user-secrets init
python --version
powershell -NoProfile -File scripts\Set-DevelopmentAdmin.ps1
dotnet ef migrations has-pending-model-changes
dotnet ef database update
dotnet run --no-build --launch-profile https
dotnet build
dotnet run --no-build --launch-profile https -- --Logging:LogLevel:Microsoft.EntityFrameworkCore.Database.Command=Warning
python scripts\verify_phase2.py
git diff --stat
git diff --check
dotnet build
dotnet ef migrations has-pending-model-changes
dotnet ef database update
```

`dotnet run` бөлек жұмыс істеп тұрғанда басқа terminal-да verification орындалады. SQL тексерулері мен тек осы іске тиесілі деректерді cleanup жасау командалары `scripts/verify_phase2.py` ішінде толық жазылған. Скриптке Python 3 және `sqlcmd` қажет; жобаға олар үшін NuGet пакеттері қосылған жоқ.
